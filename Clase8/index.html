El porqué

¿Por qué no consultar directo la base transaccional?

La base techventas está diseñada para operar: registrar ventas rápido, sin duplicar datos (normalizada). Pero para analizar —sumar, comparar por período, cruzar dimensiones— esa forma es incómoda y lenta.

OLTP · Transaccional

Optimizado para escribir: muchas operaciones pequeñas (insertar una venta). Normalizado. Es techventas.

OLAP · Analítico

Optimizado para leer y agregar: pocas consultas grandes que resumen millones de filas. Desnormalizado. Es el Data Warehouse.

Data Warehouse: un repositorio de datos orientado al análisis, integrado desde una o varias fuentes, organizado por temas (ventas, clientes…) y pensado para responder preguntas de negocio con rapidez.
El modelo que vamos a construir

Esquema estrella: hechos + dimensiones

Una tabla de hechos en el centro guarda las medidas numéricas (cantidad, total). Alrededor, las dimensiones describen el contexto: quién, qué, cuándo, dónde. Las FKs de la tabla de hechos apuntan a cada dimensión — dibujan una estrella.

Granularidad: el nivel de detalle de un hecho. Acá, una fila = una línea de venta. Definir la grano es la primera decisión del diseño.
hechos (medidas) dimensiones (contexto)
Antes de escribir código

Diccionario simple: los comandos que vas a usar

Si SQL te suena a chino, tené esta slide a mano. Cada comando explicado en una frase, con una analogía cotidiana.

CREATE DATABASE
Crea una base de datos nueva y vacía. Es como reservar un depósito vacío donde después vas a guardar cosas.
CREATE TABLE
Crea una tabla con sus columnas y tipos. Es armar una planilla vacía definiendo qué va en cada columna.
INSERT INTO … SELECT
Copia filas de una consulta hacia otra tabla. Sacás datos de un lado y los pegás en otro, todo de una.
SELECT … FROM
Lee y devuelve filas de una tabla. Es pedir "mostrame estos datos": el comando más usado de todos.
DISTINCT
Elimina filas repetidas del resultado. Si un vendedor aparece 15 veces, con DISTINCT lo ves una sola vez.
WHERE
Filtra filas según una condición. Es el "solamente los que cumplan…" (ej: WHERE ciudad = 'Salto').
GROUP BY
Junta filas que comparten un valor para resumirlas. "Agrupame por categoría" y calculás un total por cada una.
ORDER BY
Ordena el resultado. DESC = de mayor a menor, ASC = de menor a mayor. Como ordenar una lista.
JOIN … ON
Combina filas de dos tablas que se relacionan. "Pegá esta tabla con esta otra" usando la columna que tienen en común.
CREATE VIEW
Guarda una consulta con nombre para reusarla. Es un "acceso directo" a un SELECT complejo, sin duplicar datos.
SUM / COUNT
SUM suma valores; COUNT cuenta filas. Las funciones que "totalizan", casi siempre con GROUP BY.
PRIMARY KEY / FOREIGN KEY
PK = el identificador único de cada fila. FK = una columna que "apunta" a la PK de otra tabla (así se conectan).
Un patrón que verás mucho hoy: SELECT … FROM … JOIN … ON … GROUP BY … ORDER BY …. Se lee como una receta, de arriba hacia abajo.
Quiz · Conceptos

¿Hecho o dimensión?

Tres preguntas antes de escribir SQL.

1 Crear la base del DW

Un almacén aparte

El DW vive en su propia base, separada de la transaccional. Así no interferimos con la operación diaria y podemos desnormalizar con libertad.

techventas_dw.sql
CREATE DATABASE IF NOT EXISTS techventas_dw;
USE techventas_dw;
La base techventas original queda intacta como fuente. El DW la leerá para cargarse.
2 Crear las dimensiones

Las tablas del contexto

Cada dimensión tiene una clave subrogada (_key con AUTO_INCREMENT): un id propio del DW, independiente de las claves del origen. Esto da estabilidad y rendimiento a los JOINs.

dimensiones.sql
CREATE TABLE dim_producto (
    producto_key  INT AUTO_INCREMENT PRIMARY KEY,  -- clave subrogada
    producto      VARCHAR(50),
    categoria     VARCHAR(40)                -- jerarquía categoria > producto
);

CREATE TABLE dim_vendedor ( vendedor_key INT AUTO_INCREMENT PRIMARY KEY, vendedor VARCHAR(50) );
CREATE TABLE dim_ciudad   ( ciudad_key   INT AUTO_INCREMENT PRIMARY KEY, ciudad   VARCHAR(40) );
Clave subrogada vs. natural: la natural sería el nombre del producto; la subrogada es un entero sin significado de negocio. Se prefiere la subrogada porque es pequeña, estable y no cambia si el nombre se corrige.
2 La dimensión especial: tiempo

dim_tiempo, la más útil de todas

Casi todo análisis se mira "por período". Una dimensión de tiempo con jerarquía (año → trimestre → mes → día) permite en Power BI hacer drill-down sin esfuerzo. Su clave suele ser la fecha en formato AAAAMMDD.

dim_tiempo.sql
CREATE TABLE dim_tiempo (
    tiempo_key  INT PRIMARY KEY,        -- ej: 20240315
    fecha       DATE,
    anio        INT,
    trimestre   INT,
    mes         INT,
    nombre_mes  VARCHAR(15),
    dia         INT
);
3 Crear la tabla de hechos

El centro de la estrella

fact_ventas guarda las medidas (lo que se suma y promedia) más una FK a cada dimensión. Es una tabla larga y "flaca": muchas filas, pocas columnas de texto.

fact_ventas.sql
CREATE TABLE fact_ventas (
    venta_id        INT PRIMARY KEY,
    producto_key    INT,   -- FK → dim_producto
    vendedor_key    INT,   -- FK → dim_vendedor
    ciudad_key      INT,   -- FK → dim_ciudad
    tiempo_key      INT,   -- FK → dim_tiempo
    cantidad        INT,            -- ┐
    precio_unitario DECIMAL(10,2),   -- ├ MEDIDAS
    descuento_pct   INT,            -- │
    total_neto      DECIMAL(12,2),   -- ┘
    FOREIGN KEY (producto_key) REFERENCES dim_producto(producto_key)
    -- ... y las otras 3 FKs
);
Medida aditiva: total_neto se puede sumar por cualquier dimensión (por ciudad, por mes…). Guardarla ya calculada acelera el análisis.

4 Cargar los datos (ETL)

Extract · Transform · Load

Ahora poblamos el DW leyendo desde techventas. El patrón: primero las dimensiones (valores distintos), después los hechos (resolviendo cada FK con un JOIN).

etl_dimensiones.sql
-- 1) Dimensiones: los valores únicos del origen
INSERT INTO dim_producto (producto, categoria)
SELECT DISTINCT producto, categoria FROM techventas.ventas;

INSERT INTO dim_tiempo (tiempo_key, fecha, anio, trimestre, mes, nombre_mes, dia)
SELECT DISTINCT
    (YEAR(fecha)*10000 + MONTH(fecha)*100 + DAY(fecha)),
    fecha, YEAR(fecha), QUARTER(fecha), MONTH(fecha), MONTHNAME(fecha), DAY(fecha)
FROM techventas.ventas;
ETL = Extract (leer del origen) → Transform (limpiar, calcular, deduplicar con DISTINCT) → Load (insertar en el DW).
4 Poblar la tabla de hechos

JOINs que resuelven las claves

Cada fila de venta del origen se convierte en un hecho: unimos contra cada dimensión para traducir el texto (nombre del producto, del vendedor…) a su clave subrogada.

etl_hechos.sql
INSERT INTO fact_ventas (venta_id, producto_key, vendedor_key,
    ciudad_key, tiempo_key, cantidad, precio_unitario, descuento_pct, total_neto)
SELECT
    v.id_venta, dp.producto_key, dv.vendedor_key, dc.ciudad_key,
    (YEAR(v.fecha)*10000 + MONTH(v.fecha)*100 + DAY(v.fecha)),
    v.cantidad, v.precio_unitario, v.descuento_pct,
    ROUND(v.precio_unitario * v.cantidad * (1 - v.descuento_pct/100), 2)
FROM techventas.ventas v
JOIN dim_producto dp ON dp.producto = v.producto AND dp.categoria = v.categoria
JOIN dim_vendedor dv ON dv.vendedor = v.vendedor
JOIN dim_ciudad   dc ON dc.ciudad   = v.ciudad;
Verificá con SELECT COUNT(*) FROM fact_ventas; → deben ser 2.000 hechos, uno por venta original.
5 Crear vistas analíticas

Vistas: la cara amable del DW

Power BI podría leer las tablas crudas, pero las vistas le entregan datos ya unidos y legibles. La vista estrella "desnormalizada" reúne todo en una sola consulta.

vistas.sql
CREATE VIEW vw_ventas_dw AS
SELECT f.venta_id, t.fecha, t.anio, t.nombre_mes,
       p.producto, p.categoria, ve.vendedor, c.ciudad,
       f.cantidad, f.total_neto
FROM fact_ventas f
JOIN dim_tiempo   t  ON t.tiempo_key   = f.tiempo_key
JOIN dim_producto p  ON p.producto_key = f.producto_key
JOIN dim_vendedor ve ON ve.vendedor_key = f.vendedor_key
JOIN dim_ciudad   c  ON c.ciudad_key   = f.ciudad_key;
El script también crea vw_ventas_por_categoria y vw_ventas_por_mes ya agregadas — ideales para gráficos directos.
6 Integrar a Power BI

Del DW al dashboard

  • Obtener datos → Base de datos MySQL, servidor localhost, base techventas_dw.
  • En el Navegador, cargá las vistas (vw_ventas_dw y las agregadas).
  • Si cargás las tablas del estrella, Power BI detecta las relaciones por las claves — revisalas en la vista Modelo.
  • Armá los visuales: total por categoría, serie por mes, ranking de vendedores.
Modelo en Power BI

El esquema estrella se traduce naturalmente al modelo de datos de Power BI: la tabla de hechos en el centro, dimensiones alrededor, relaciones 1‑a‑muchos. Es exactamente el modelo que Power BI prefiere para rendir bien.

La dim_tiempo te habilita drill-down temporal: hacé clic en un año y bajá a trimestre, mes y día en el mismo gráfico.
