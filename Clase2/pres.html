¿Qué es una base de datos relacional?

Un conjunto de datos organizados en tablas (relaciones) que se vinculan entre sí. Propuesto por E. F. Codd en 1970, sigue siendo el modelo dominante para datos estructurados.

Tablas

Cada tabla representa una entidad del negocio: clientes, productos, ventas.

Relaciones

Las tablas se conectan mediante claves: un dato vive en un solo lugar y se referencia desde otros.

SQL

Un lenguaje declarativo y estándar para consultar y manipular esos datos. Decís qué querés, no cómo obtenerlo.

anticipo de la noche
SELECT nombre, ciudad FROM clientes WHERE ciudad = 'Montevideo';

Transacciones: todo o nada

Una transacción es una unidad de trabajo: un conjunto de operaciones que deben ejecutarse como un bloque indivisible.

transferencia.sql
START TRANSACTION;

-- Ana le transfiere $1000 a Bruno
UPDATE cuentas SET saldo = saldo - 1000 WHERE titular = 'Ana';
UPDATE cuentas SET saldo = saldo + 1000 WHERE titular = 'Bruno';

COMMIT;   -- confirma TODO…
-- o ROLLBACK; deshace TODO
¿Qué pasaría sin transacción?

Si el sistema se cae entre los dos UPDATE: a Ana le descontaron $1000… y Bruno nunca los recibió. El dinero "desapareció".

Con transacción

O se ejecutan las dos operaciones, o ninguna. El motor garantiza que la base nunca queda a mitad de camino.

Modelado de datos

Las 4 garantías: A·C·I·D

A
Atomicidad

La transacción es indivisible: se completa entera o no deja rastro. Todo o nada.

C
Consistencia

La base pasa de un estado válido a otro estado válido: nunca viola sus reglas (saldos, claves, restricciones).

I
Aislamiento

Las transacciones simultáneas no se pisan entre sí: cada una ve la base como si estuviera sola.

D
Durabilidad

Una vez confirmada (COMMIT), la transacción sobrevive a cortes de luz y caídas del sistema.

Pensalo así

Una compra online: descontar stock + registrar el pedido + cobrar la tarjeta. ACID garantiza que jamás cobres sin registrar el pedido, ni vendas un producto sin stock que otro cliente acaba de llevarse.

Normalización

¿Por qué normalizar? Una tabla con problemas

Esta tabla "funciona"… hasta que hay que mantenerla. Encontrá los problemas:

pedidoclienteemail_clienteproductosciudad_cliente
101Lucía Pérezlucia@mail.comTeclado, Mouse, MonitorMontevideo
102Diego Sosadiego@mail.comMouseSalto
103Lucía Pérezlucia@gmail.comNotebookMontevdeo
Anomalía de actualización

El cliente se repite en cada pedido. Si cambia su email, hay que corregirlo en N filas… y en la fila 103 ya quedó distinto.

Anomalía de inserción

No puedo registrar un cliente nuevo hasta que haga un pedido: no hay dónde ponerlo.

Anomalía de borrado

Si borro el pedido 102, pierdo también los datos de Diego: era su único pedido.

¿Y notaste "Montevdeo" en la fila 103? La redundancia invita al error. La normalización lo previene por diseño.

Normalización

Primera Forma Normal (1FN)

Normalización

Segunda Forma Normal (2FN)

Estando en 1FN: ningún atributo depende de una parte de la clave. Cada dato depende de la clave completa.

Viola 2FN — clave: (pedido, producto)

Normalización

Tercera Forma Normal (3FN)

Estando en 2FN: ningún atributo depende de otro atributo que no sea clave. Sin dependencias transitivas.

Viola 3FN
cliente_idnombrecod_ciudadnombre_ciudad
1LucíaMVDMontevideo
3MartaMVDMontevideo

nombre_ciudad depende de cod_ciudad (no de la clave) → cadena: clave → cod_ciudad → nombre_ciudad.

Cumple 3FN — tabla de ciudades

MVDMontevideo
Regla mnemotécnica

Cada atributo depende de la clave (1FN), de toda la clave (2FN) y de nada más que la clave (3FN).

Reglas de integridad

Clave primaria (PK)

Identifica de forma única e inequívoca a cada fila. Es la base de la integridad de entidad.

clientes.sql
CREATE TABLE clientes (
  id     INT AUTO_INCREMENT,
  nombre VARCHAR(100) NOT NULL,
  email  VARCHAR(120) UNIQUE,
  ciudad VARCHAR(60),
  PRIMARY KEY (id)
);
  • Única: no puede repetirse en dos filas.
  • No nula: toda fila debe tenerla (NOT NULL implícito).
  • Estable: idealmente no cambia nunca → por eso solemos usar un id autoincremental y no el email o la cédula.
  • Puede ser compuesta: varias columnas juntas, como (pedido_id, producto_id) en una tabla intermedia.
Para discutir

¿Por qué la cédula de identidad puede ser una mala PK para clientes? (extranjeros, errores de tipeo, datos sensibles…)

Clave foránea (FK) e integridad referencial

Una columna que apunta a la PK de otra tabla. El motor garantiza que la referencia siempre exista: integridad referencial.

pedidos.sql
CREATE TABLE pedidos (
  id         INT AUTO_INCREMENT PRIMARY KEY,
  cliente_id INT NOT NULL,
  fecha      DATE,
  FOREIGN KEY (cliente_id) REFERENCES clientes(id)
);
Qué impide el motor
  • Insertar un pedido con cliente_id = 99 si ese cliente no existe.
  • Borrar un cliente que todavía tiene pedidos (salvo que definas ON DELETE).
Pedidos huérfanos = reportes rotos

Para un analista, una FK rota significa ventas que no suman en ningún cliente. La integridad referencial es tu seguro de calidad de datos.

CRUD · Read

SELECT — consultar datos

select.sql
-- todas las columnas, todas las filas
SELECT * FROM clientes;

-- solo algunas columnas
SELECT nombre, email FROM clientes;

-- con filtro
SELECT * FROM clientes
WHERE ciudad = 'Montevideo';

-- ordenado y limitado
SELECT nombre FROM clientes
ORDER BY nombre ASC
LIMIT 10;
  • * = todas las columnas. Útil para explorar; en producción se prefieren columnas explícitas.
  • WHERE filtra filas con condiciones: =, <>, >, <, LIKE, IN, BETWEEN.
  • Los textos van entre comillas simples; los números, sin comillas.
  • ORDER BY ordena, LIMIT recorta.
  • SQL no distingue mayúsculas en las palabras clave, pero la convención es escribirlas en MAYÚSCULAS.
CRUD · Create

INSERT — agregar filas

insert.sql
-- forma recomendada: columnas explícitas
INSERT INTO clientes (nombre, email, ciudad)
VALUES ('Ana Ruiz', 'ana@mail.com', 'Salto');

-- varias filas de una vez
INSERT INTO productos (nombre, precio)
VALUES ('Teclado', 1200),
       ('Mouse',   800);
  • Listar las columnas hace el INSERT robusto: si mañana la tabla agrega una columna, tu sentencia sigue funcionando.
  • El id AUTO_INCREMENT no se incluye: lo genera el motor.
  • El orden de los VALUES debe coincidir con el orden de las columnas declaradas.
  • Si violás una regla (email UNIQUE repetido, FK inexistente) el motor rechaza la fila: la integridad en acción.
CRUD · Update & Delete

UPDATE y DELETE — con cuidado

update-delete.sql
-- modificar
UPDATE productos
SET precio = 1500
WHERE id = 1;

-- eliminar
DELETE FROM clientes
WHERE id = 5;
La regla de oro

Un UPDATE o DELETE sin WHERE afecta TODAS las filas de la tabla. Es el error clásico que arruina viernes a la tarde.

Truco profesional

Antes del UPDATE/DELETE, ejecutá un SELECT con el mismo WHERE. Si devuelve exactamente las filas que querés tocar, recién ahí ejecutás. Y mejor aún: dentro de una transacción.
